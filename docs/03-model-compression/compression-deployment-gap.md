# 从压缩率到真实加速：部署鸿沟

## 核心问题

参数量下降、非零元素减少或理论运算量降低，并不自动产生真实加速。

## 常见原因

- 框架仍以高精度 Tensor 存储或计算。
- 运行时需要在线反量化。
- 非结构化稀疏缺少高效 Kernel。
- 稀疏索引和不规则访存引入额外开销。
- 模型太小，Kernel launch 或 Python 调度占主导。
- Decode 受内存带宽限制，计算量降低收益有限。
- 多 GPU 通信成为新的瓶颈。
- 动态 shape 破坏编译或 CUDA Graph 的收益。

## 必须回答的问题

```text
压缩后保存的实际格式是什么？
执行时调用了哪个 Kernel？
是否减少了 HBM 读取量？
是否改变了 GEMM shape？
是否引入 dequant 或 sparse metadata 开销？
优化作用于 Prefill、Decode，还是二者？
端到端服务性能是否改善？
```
